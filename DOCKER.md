# MELLCOIN в Docker — как это работает

Инструкция с пояснениями: что за файлы появились, зачем каждый нужен и
почему сделано именно так.

---

## 1. Мысленная модель: четыре понятия

Прежде чем команды — четыре слова, которые постоянно путают.

**Dockerfile** — рецепт. Текстовый файл с шагами: возьми Node 22, скопируй
файлы, выполни `npm ci`, собери. Сам по себе ничего не делает.

**Образ (image)** — результат исполнения рецепта. Замороженный слепок
файловой системы: Node, ваш код, node_modules. Только для чтения, ничего
не выполняет. Аналогия — установочный ISO.

**Контейнер (container)** — запущенный экземпляр образа. Из одного образа
можно поднять хоть десять контейнеров. Аналогия — виртуалка, загруженная
с того ISO.

**docker-compose.yml** — оркестратор. Описывает, какие сервисы поднять,
как они связаны, какие порты и переменные им дать. Без него пришлось бы
вручную писать длинные `docker run` и вручную создавать сеть.

Отсюда сразу следствие, на котором все спотыкаются:

> Правка исходников **не влияет** на работающий контейнер.
> Внутри лежит код, вмороженный в образ на момент сборки.
> Чтобы изменения доехали — нужна **пересборка образа**, а не рестарт.

## 2. Запуск

Docker Desktop должен быть запущен (иконка кита в трее — не серая).

```bash
npm run docker:up
```

Одна команда: соберёт образы, если их нет, и поднимет все три сервиса.
Под капотом `docker compose up -d --build`.

Первый запуск — 2-4 минуты (скачиваются базовые образы Node, nginx,
Postgres). Дальше — секунды.

Проверить, что всё встало:

```bash
npm run docker:ps
```

Должно быть три строки со статусом `healthy`:

```
SERVICE    STATUS                   PORTS
client     Up 2 minutes (healthy)   0.0.0.0:8080->80/tcp
postgres   Up 2 minutes (healthy)   0.0.0.0:5433->5432/tcp
server     Up 2 minutes (healthy)   0.0.0.0:3000->3000/tcp
```

Открывайте **http://localhost:8080**

Остановить:

```bash
npm run docker:down
```

Контейнеры удалятся, **данные игроков останутся** — они в именованном томе.
Полный сброс вместе с базой: `npm run docker:reset`.

## 3. Что происходит при запуске

```
docker compose up -d --build
        │
        ├─ 1. Создаёт сеть telegram_game_default
        │
        ├─ 2. Собирает образ server (server/Dockerfile)
        ├─ 3. Собирает образ client (client/Dockerfile)
        │
        ├─ 4. Поднимает postgres        ──> ждёт pg_isready
        │                                        │ healthy
        ├─ 5. Поднимает server  <────────────────┘
        │       (depends_on: postgres healthy)
        │       ──> ждёт GET /api/health
        │                                        │ healthy
        └─ 6. Поднимает client  <────────────────┘
                (depends_on: server healthy)
```

`depends_on` с `condition: service_healthy` — важная деталь. Без него Docker
считает сервис готовым, как только процесс стартовал. Postgres при этом ещё
инициализируется, NestJS не может подключиться и падает. Мы ждём именно
**healthcheck**, а не факт запуска.

## 4. Три вещи, на которых спотыкаются все

### 4.1. У базы два разных адреса

Это причина ошибки №1 у новичков.

| Откуда обращаемся | Адрес базы |
| --- | --- |
| Из контейнера `server` | `postgres:5432` |
| С вашего Windows (DBeaver, psql, `npm run dev`) | `localhost:5433` |

Внутри сети Docker **имя сервиса работает как доменное имя**. `server`
обращается к `postgres:5432` — это внутренний порт контейнера.

Секция `ports: "5433:5432"` (читается «снаружи:внутри») нужна **только**
чтобы достучаться с хоста. Контейнерам между собой она не нужна вообще.

Поэтому в `docker-compose.yml` у сервера стоит:

```yaml
DB_HOST: postgres      # не localhost!
DB_PORT: 5432          # не 5433!
```

`localhost` внутри контейнера означает «этот самый контейнер», а не ваш
компьютер. Postgres там не живёт — будет `ECONNREFUSED`.

**Исключение — фронтенд.** В `VITE_API_URL` стоит `http://localhost:3000`,
и это правильно: этот адрес открывает **браузер пользователя**, а он
находится вне сети Docker. Имя `server` он не разрешит.

### 4.2. Переменные Vite подставляются при СБОРКЕ

NestJS читает `process.env` в момент запуска — можно поменять переменную
в compose и просто перезапустить.

С Vite так не работает. `import.meta.env.VITE_API_URL` **заменяется на
строку прямо в JS-файле** при сборке бандла. После сборки менять нечего.

Поэтому адрес API у клиента передаётся через `args` (аргумент сборки),
а не через `environment`:

```yaml
client:
  build:
    args:
      VITE_API_URL: http://localhost:3000
```

Проверить, что зашилось:

```bash
curl -s http://localhost:8080/ | grep -o '/assets/index-[^"]*\.js'
```

и поискать адрес в этом файле.

**Меняли `VITE_API_URL` — нужна пересборка**, рестарт не поможет.

### 4.3. Когда пересобирать, а когда перезапускать

| Что поменяли | Что делать |
| --- | --- |
| Код в `server/src` или `client/src` | пересборка: `npm run docker:up` |
| `package.json` (зависимости) | пересборка |
| `Dockerfile`, `nginx.conf` | пересборка |
| `environment:` у сервера в compose | `docker compose up -d` (без `--build`) |
| `args:` у клиента в compose | пересборка |

`npm run docker:up` включает `--build`, так что в сомнительном случае
запускайте его — Docker сам пропустит неизменившиеся слои по кешу.

## 5. Разбор Dockerfile сервера

Файл [`server/Dockerfile`](server/Dockerfile) — три стадии. Зачем так сложно?

Если собрать «в лоб» одной стадией, в итоговый образ попадёт весь
инструментарий сборки: TypeScript, `@nestjs/cli`, webpack. Всё это нужно
ровно один раз — чтобы скомпилировать. В рантайме это мёртвый груз.

**Многостадийная сборка** решает это так: `FROM` можно писать несколько раз,
а `COPY --from=<стадия>` переносит файлы между ними. В финальный образ
попадает только то, что явно скопировали.

```
Стадия build   ── ставит всё, компилирует TS ──> server/dist
Стадия deps    ── ставит только прод-зависимости ──> node_modules
                                    │
Стадия runtime <────────────────────┘  берёт только эти два результата
```

### Порядок COPY — это про кеш

```dockerfile
COPY package.json package-lock.json ./
COPY server/package.json ./server/
COPY client/package.json ./client/
RUN npm ci --workspace server --include-workspace-root

COPY server ./server          # <- код копируется ПОСЛЕ установки
RUN npm run build --workspace server
```

Docker кеширует каждую инструкцию. Если файл не изменился — шаг берётся
из кеша. Манифесты меняются редко, код — постоянно. При таком порядке
правка в коде сбрасывает кеш только с шага `COPY server`, а долгий
`npm ci` переиспользуется.

Скопируй мы всё одной строкой `COPY . .` — любая правка запускала бы
переустановку зависимостей заново. Сборка вместо 10 секунд занимала бы
две минуты.

### Почему контекст сборки — корень проекта

```yaml
build:
  context: .                    # корень, не ./server
  dockerfile: server/Dockerfile
```

Dockerfile не может копировать файлы **выше контекста**. Проект — npm
workspaces, `package-lock.json` лежит в корне и описывает оба пакета.
Из контекста `./server` до него не дотянуться.

Отсюда же `--workspace server`: лок общий на оба пакета, и без этого флага
в серверный образ приехали бы ещё и React с Vite.

### Мелочи, которые стоит знать

- **`EXPOSE 3000`** — это документация, а не открытие порта. Реально порт
  публикует только `ports:` в compose.
- **`USER node`** — не запускаем от root. В образах `node` этот пользователь
  уже создан.
- **`CMD ["node", "dist/main"]`** массивом, а не строкой. Так процесс
  становится PID 1 и получает `SIGTERM` напрямую. Через строку сигнал ушёл
  бы в `sh`, и Nest не успел бы отработать `enableShutdownHooks` — а у нас
  на выключении сбрасывается состояние игроков в БД.

## 6. Разбор Dockerfile клиента

Ключевая мысль: **React после сборки — это статика**. index.html, js, css.
Node для их отдачи не нужен.

Поэтому финальный образ — nginx (74 МБ), а не Node (был бы ~250 МБ).

### SPA-fallback — зачем нужен nginx.conf

```nginx
location / {
    try_files $uri $uri/ /index.html;
}
```

У нас клиентский роутинг: адрес `/login` существует только в React, файла
на диске нет. Без этой строки перезагрузка страницы на `/login` дала бы 404.

`try_files` говорит: попробуй такой файл → попробуй папку → отдай
`index.html`. Дальше React сам разберётся с адресом.

### Кеширование

Vite добавляет хеш в имена файлов: `index-BgiR8R3-.js`. Изменилось
содержимое — изменилось имя. Такие файлы можно кешировать навсегда.

А `index.html` кешировать **нельзя**: в нём ссылки на текущие хеши.
Закешированный index указывал бы на старые файлы, которых уже нет.

## 7. Что пришлось поменять в коде

Две настройки были завязаны на `NODE_ENV`, и в контейнере это сломалось бы.

В контейнере стоит `NODE_ENV=production` — это нормально и правильно.
Но раньше из этого следовало:

1. `synchronize: NODE_ENV !== 'production'` → схема БД не создалась бы,
   приложение упало бы на первом запросе;
2. `secure: NODE_ENV === 'production'` у куки → браузер принимает такие
   куки **только по HTTPS**. Локально мы ходим по http — кука молча не
   сохранилась бы, вход «не работал» бы без единой ошибки в логах.

Стало — отдельные переменные, которые ничего не выводят из `NODE_ENV`:

| Переменная | В Docker | Смысл |
| --- | --- | --- |
| `DB_SYNCHRONIZE` | `true` | Автосоздание схемы. Для реального прода — `false` + миграции |
| `COOKIE_SECURE` | `false` | `true` только когда есть HTTPS |
| `COOKIE_SAMESITE` | `lax` | При `COOKIE_SECURE=true` нужно `none` |

Общий урок: **`NODE_ENV` — плохой переключатель для всего сразу.**
Он смешивает «оптимизировать сборку» с «мы за HTTPS» и «схема уже есть».
Это разные вопросы, и у каждого должен быть свой флаг.

## 8. Повседневные команды

```bash
npm run docker:logs
```

Логи всех сервисов в реальном времени. Выход — `Ctrl+C`.

Логи одного сервиса:

```bash
docker compose logs -f server
```

Последние 50 строк без слежения:

```bash
docker compose logs --tail 50 server
```

Зайти внутрь контейнера — посмотреть, что там на самом деле:

```bash
docker compose exec server sh
```

Внутри обычная оболочка: `ls /app/server/dist`, `env`, `cat package.json`.
Выход — `exit`.

Открыть psql в контейнере базы:

```bash
docker compose exec postgres psql -U mellcoin -d mellcoin
```

Перезапустить один сервис:

```bash
docker compose restart server
```

Пересобрать только сервер:

```bash
docker compose up -d --build server
```

Посмотреть размеры образов:

```bash
docker images | grep telegram_game
```

## 9. Типовые ошибки

**`Cannot connect to the Docker daemon`**
Не запущен Docker Desktop. Запустите и дождитесь, пока иконка перестанет
быть серой.

**`port is already allocated`**
Порт занят. Чаще всего вы не остановили `npm run dev` — там свой сервер
на 3000. Найти виновника: `netstat -ano | findstr :3000`, затем закрыть
процесс. Или поменяйте порт в `ports:` на свободный.

**Сервер перезапускается по кругу, в логах `ECONNREFUSED`**
Не резолвится база. Проверьте, что в compose стоит `DB_HOST: postgres`,
а не `localhost`, и `DB_PORT: 5432`, а не `5433`. См. п. 4.1.

**Клиент открывается, но «связь…» и вход не работает**
Смотрите вкладку Network в браузере. Скорее всего:
- запросы уходят не на тот адрес → пересоберите с верным `VITE_API_URL`;
- ошибка CORS → в compose у сервера `CLIENT_ORIGIN` должен совпадать
  с адресом в браузере (`http://localhost:8080`);
- запросы проходят, но `/api/auth/me` даёт 401 → кука не сохранилась,
  проверьте `COOKIE_SECURE: "false"`.

**Правки в коде не видны**
Вы перезапустили контейнер вместо пересборки образа. `npm run docker:up`.

**Место на диске**
Старые образы и слои копятся. Чистка: `docker system prune -a`
(осторожно: удалит все неиспользуемые образы, не только этого проекта).

## 10. Docker или npm run dev?

Оба варианта рабочие, но для разного.

**`npm run dev`** — для написания кода. Hot reload: сохранили файл, через
секунду видите результат. Docker так не умеет (в этой конфигурации —
образ пересобирается целиком).

При этом база всё равно нужна:

```bash
npm run db:up     # поднимает только postgres
npm run dev
```

Клиент на http://localhost:5173, сервер на 3000.

**`npm run docker:up`** — чтобы проверить систему в том виде, в котором она
поедет на сервер: прод-сборка, nginx, реальные переменные окружения.
И чтобы отдать проект другому человеку: у него всё поднимется одной
командой, без установки Node и Postgres.

**Одновременно они конфликтуют** за порт 3000. Перед `docker:up` остановите
`npm run dev`, и наоборот.

## 11. Что дальше

Когда дойдёт до реального сервера, понадобится:

- **Миграции вместо `synchronize`** — сейчас TypeORM меняет схему сам,
  и на проде это может молча удалить колонку с данными.
- **HTTPS** — а вместе с ним `COOKIE_SECURE=true` и `COOKIE_SAMESITE=none`.
- **Секреты не в compose** — `JWT_SECRET` сейчас лежит открытым текстом
  в файле. На проде это переменные окружения хостинга или Docker secrets.
- **Reverse proxy перед всем** — один nginx/Traefik на 443, который
  раздаёт статику и проксирует `/api` и `/socket.io` на бэкенд.
  Тогда клиент и API окажутся на одном origin: CORS не нужен вообще,
  а `VITE_API_URL` можно оставить пустым.
- **Redis для socket.io**, если инстансов сервера будет больше одного —
  сейчас состояние игроков живёт в памяти одного процесса.
